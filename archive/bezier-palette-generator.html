Week 2 Experiment: Bézier Curves and a Palette Generator

10 oct 20262026 年 10 月 10 日

这篇文章写于在学校的课程期间，原文是英文。

In the previous experiment I went from 576 ocean photos to one brand blue, #005AEB, and from there to ten core colours, each marked as C6. A single colour is not yet a system, though. A real interface needs about ten steps of every colour: dark ones for text, light ones for backgrounds, and in-between ones for borders, hover states and charts. That is 100 colours for light mode and another 100 for dark mode.

Picking 200 colours by hand would be slow, and worse, it would be inconsistent. So I built a small tool, Palette Curve Lab, that learns the rhythm of good existing colour scales with cubic Bézier curves and applies it to any new C6. The code is on my GitHub: github.com/QingzhouC/color_palette_tool. Every chart and swatch in this post is drawn from that code and its reference database, not mocked up.

01 · Why not just interpolate?

The obvious way to make a scale is to take C6, a dark end and a light end, and space the steps evenly in RGB. It is easy, and for a blue it even looks acceptable. But look at the chroma, the colourfulness, of each step:

In straight RGB steps, chroma falls the moment you leave C6: C5 drops to 69, while the model keeps it at 76. On screen this is the difference between a hover colour that feels like the brand and one that feels slightly washed out. RGB steps also treat every hue the same way, but a yellow and a blue do not lighten the same way to the eye (this was the brightness problem from my last post). The steps have to follow perception, not channels.

02 · Learning from reference scales

Working in LCH

The generator describes every colour in CIE LCH(ab), the polar form of Lab: L is lightness, C is chroma and H is hue angle. The reason is practical. In RGB, “lighter”, “greyer” and “shifting hue” are tangled together across three channels. In LCH they are three separate numbers, so I can model each change on its own.

The reference cards

The tool reads a set of existing, hand-tuned scales from a small SQLite database (palettes.db), with separate sets for light and dark mode. Each is ten steps, C10 to C1, with C6 as the core. These are the “good examples” the model learns from:

Making scales comparable

A dark blue and a bright yellow have completely different numbers, so the model cannot learn from raw values. It describes every step relative to its own C6:

  • Lightness on the dark side (C10→C6) as a ratio, L / L₆; on the light side (C6→C1) as progress towards white, (L − L₆) / (100 − L₆).
  • Chroma as a ratio, C / C₆, so “keep 90% of the colourfulness” means the same thing for every hue.
  • Hue as an offset, H − H₆, measured the short way round the circle so that crossing 0° never causes a fake 350° jump.

The scale is also split at C6 into two halves, C10→C6 (five points) and C6→C1 (six points), and each half gets its own curves. One curve through all ten steps would have to bend through the core colour and would lose control on one side.

03 · Fitting cubic Bézier curves

A cubic Bézier curve is defined by four points:

P(t) = (1−t)³P₀ + 3(1−t)²t P₁ + 3(1−t)t² P₂ + t³P₃, t ∈ [0, 1]

P₀ and P₃ are the ends; P₁ and P₂ pull the middle of the curve without the curve passing through them (Farin, 2002). Designers know this shape from the pen tool and from CSS easing, which is why I chose it: it describes the rhythm of a change, whether it starts slowly and speeds up or the reverse, using only two free numbers.

Here, I am not drawing a line on the screen. For every half and every channel (L, C, H), the reference steps become a series of values at evenly spaced t. The two ends are fixed to the real first and last value. Then least squares finds the P₁ and P₂ that make the curve pass as close as possible to all the reference steps. Because P₀ and P₃ are known, this is a small linear problem with two unknowns, solved in one step with numpy.linalg.lstsq.

These are the six curves fitted to the light-mode blue reference scale, the scale the brand blue is built from. Coloured dots are the real reference colours, the black line is the fitted curve, and the squares are its control points (hollow squares are the fitted P₁ and P₂):

Reading the curves taught me things about the reference scale that I had never noticed by eye:

  • Light-side lightness starts almost flat (P₁ = 0.09) and then rises steeply. The first step up from C6 is small, so C5 stays close to the brand colour, and the big jumps happen in the pale end.
  • Light-side chroma stays high (P₁ = 0.94) and then collapses. The colour holds its strength for a while and drops all at once, exactly what straight RGB steps fail to do.
  • Hue is not constant. Towards C1 the blue turns about 24° in LCH hue. A good pale blue leans slightly more towards cyan than its core, otherwise it starts to read as lavender. A designer did this by instinct; the curve makes it explicit.

Applying the curves to a new C6

To generate a scale, the tool takes the new C6 in LCH, evaluates each curve at the same t values, turns the relative values back into absolute L, C and H, and converts each step to HEX. The tool also limits lightness and converts into the displayable sRGB range safely, so that a curve that overshoots never produces a colour the screen cannot show. C6 itself is never changed. It is always exactly the input HEX.

04 · Adapting to hue

A single model would not work for all ten groups, because colours do not age the same way. A yellow must darken towards olive, and a red towards brown; a blue mostly just deepens. So the tool keeps one fitted model per reference scale and blends them depending on how close their C6 hue is to the new colour:

wk = exp(−dk² / 2σ²) / Σj exp(−dj² / 2σ²)

dk is the circular hue distance to reference k. A Gaussian means nearby hues dominate, but there is no hard switch between models.

parametervaluewhat it does
hue range σ35°how far a reference’s influence reaches
adaptive strength0.7575% local hue-weighted model, 25% the median of all models, so a few references cannot make the curves swing wildly
anchor match≤ 1°if the new hue is within 1° of a reference, use that reference’s model directly

05 · The full light palette

Looking down the columns is the real test. If the system works, each column should feel like one “weight”: all the C8s work as strong text, all the C2s as soft backgrounds. They are not identical in lightness (yellow C6 is far lighter than violet C6, on purpose), but the rhythm between neighbouring steps is shared, because it comes from the same family of curves.

06 · From light to dark

Why the shortcuts fail

The tempting way to make dark mode is to reuse the light scale: darken everything, or simply flip it. Both look wrong in practice:

Darkening everything makes the whole palette muddy, and the core colour loses its glow on a dark background. Flipping keeps the light-mode C6, which is too intense on black, and the steps were tuned for white paper, not a dark screen. Saturated colours on a dark background also seem to vibrate. So dark mode needs its own C6 and its own curves.

Step 1 · a dark-mode C6

The dark C6 is calculated in HSB. Hue and brightness stay the same; only saturation is reduced, by percentage points (not multiplied):

Sdark = max(0, Slight − 15) for H in 0°–49° and 191°–360°
Sdark = max(0, Slight − 20) for H in 50°–190°

The green-yellow-cyan range loses a little more, because those hues glow the most on a dark screen. Three colours had results I was not happy with, so they have visually calibrated overrides instead: Purple, Red and Green.

Step 2 · dark reference curves, reversed direction

The dark C6 then goes through the same Bézier machinery, but with models fitted to dark-mode reference scales, and with the direction reversed. In dark mode, C10 is the lightest step (text on a dark background) and C1 is the darkest (surfaces). The normalisation flips with it: lightness on the C10→C6 side is measured as progress towards white, and on the C6→C1 side as a ratio of L₆.

Comparing the two sets of curves was the clearest proof that “dark mode = inverted light mode” is wrong. In the dark reference, the hue drifts by about 18° on the pale side, and the darkest steps keep about half of the core’s chroma (P₃ = 0.50), while the palest light-mode steps keep only 9%. Dark surfaces stay noticeably blue instead of collapsing into neutral black.

07 · Checking and shipping

Contrast

Every generated colour gets a WCAG contrast check against white and black (W3C, 2023). The channels are linearised, relative luminance is L = 0.2126R + 0.7152G + 0.0722B, and contrast = (Llighter + 0.05) / (Ldarker + 0.05), from 1:1 to 21:1. The tool labels AAA ≥ 7, AA ≥ 4.5 and AA Large ≥ 3:

Some practical rules came straight out of this table. In light mode, the brand C6 passes AA on white (5.7:1), so it works for buttons and links, but C5 (4.4:1) falls just below AA, so a hover state that lightens the brand needs care with any text on it. C7 and darker reach AAA for body text. In dark mode, the dark C6 #2370EB only just passes AA on black (4.6:1), so for long text on dark surfaces C8–C10 are the safer choice. The numbers are a quick filter, not the final answer. Real text still needs checking against its actual background, size and weight.

From tool to design file

The tool lets you switch between HEX, RGB and HSL, copy any colour with one click, change any C6 and regenerate that group’s light and dark scales, or reset to the defaults. Everything exports as JSON and as colour tokens for Figma, so the result goes straight into the design file and into code instead of being retyped by hand.

Reflection

The most useful thing about using Bézier curves was not automation. It was that they turned a designer’s instinct into something I could read. I had used the reference blue scale for months without noticing that its hue turns towards the pale end, or that its chroma holds and then drops suddenly. Fitting the curves made those habits visible, and once they are visible they can be discussed, kept or changed.

Kane describes how colour on computers moved from open experiment to closed, standardised software (Kane, 2014). This project sits right inside that tension, because a palette generator is a machine for standardising. What I tried to do differently is keep the machine transparent: the references, the curves and the rules are all visible and editable, and the overrides for Purple, Red and Green are written down rather than hidden. The standard is still a standard, but people can argue with it.

I also want to be honest about where the method is weak. The model can only be as good as its reference scales. Orange, which has no exact reference, depends on a blend, and its dark end is the group I would still review by hand. The dark C6 rule is also a simple HSB offset that needed three manual exceptions, which suggests a perceptual rule in LCH or OKLCH might be better. That is my next step: test whether fitting the same curves in OKLCH, the space from my reading post, needs fewer exceptions.
